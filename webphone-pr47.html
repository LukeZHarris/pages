Stop tearing our own ICE restart in half

When a call's media path dropped, our WebRTC peer was doing an ICE restart and our SIP stack was also doing one — at the same time, against the same peer connection. The next call was silent. This PR hands the whole offer/answer back to SIP.js, debounces transient blips, and cleans up after itself.

TL;DR

What the bug was
Old iceRestart() manually called restartIce(), createOffer(), and setLocalDescription() on the raw RTCPeerConnection, then asked SIP.js to send a re-INVITE. SIP.js builds its own offer when you call invite(), so the peer connection got mutated twice and ended up half-renegotiated.
What the fix is
Pass iceRestart: true through sessionDescriptionHandlerOptions.offerOptions and let SIP.js run the entire offer/answer. We just listen for the final 2xx/4xx via requestDelegate.
Why debounce
Per spec, iceConnectionState === 'disconnected' is transient — ICE often recovers on its own within a couple of seconds (Wi-Fi handoffs, brief packet loss). We now wait 3 s before issuing a re-INVITE; 'failed' still restarts immediately.
Why the timeout bump
iceGatheringTimeout went from 500 ms → 3000 ms so the restart offer actually has time to gather TURN/relay candidates before SIP.js sends it. 500 ms was reliably producing offers with only host candidates.

30-second primer (if you don't live in WebRTC)

ICE connection states

The browser publishes the health of the media path as a state machine on RTCPeerConnection. The states we care about:

connected / completed media is flowing
disconnected packets missed; may recover
failed can't proceed without restart
closed session over

What an "ICE restart" is

A fresh round of candidate gathering using new credentials, signalled to the far end via a SIP re-INVITE that carries a new SDP offer. The re-INVITE rides the existing dialog — the call doesn't drop.

In SIP.js: call session.invite() on an established session and pass offerOptions: { iceRestart: true }.

Why SIP.js has to own the offer

SIP.js's SessionDescriptionHandler tracks rollback state and pending transactions. If you mutate the underlying RTCPeerConnection directly and then let SIP.js build an offer, SIP.js's view of "what we last offered" diverges from reality — symptom: silent audio on the next call.

Old flow — two actors writing to the same peer connection
New flow — one actor, one offer/answer round-trip

How to convince yourself this works

Reproducing the original bug

On main, dial a call, then trigger an ICE restart (block UDP briefly via firewall, or toggle Wi-Fi). Hang up. Dial again — the next call is silent in one direction. That's the renegotiated PC state leaking into the next session.

Verifying the fix on this branch

Same sequence — next call has audio.

Plus, in Chrome DevTools' chrome://webrtc-internals, you should see:

  • A single setLocalDescription call per restart, not two
  • iceconnectionstate walks disconnected → checking → connected after the re-INVITE
  • For brief blips, disconnected → connected with no re-INVITE at all (the debounce caught it)

Scenarios worth manually exercising

  • Wi-Fi handoff mid-call — should trigger disconnected, then self-recover; no re-INVITE.
  • Hard network drop > 3 s — debounce expires, re-INVITE goes out, audio resumes.
  • Permanent break — eventually failed; immediate re-INVITE; if it rejects, status shows the code.
  • Hang up while a re-INVITE is in flight — no crash; SessionState guard prevents follow-on calls.
